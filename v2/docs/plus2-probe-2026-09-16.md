# +2 probe — 2026-09-16 (Wave 4.0 Packet 6)

Was Wave 3.9 Packet 9. Read-only. Base `main @ 6e3b7bf` (#98). Engine
decision paths, `docs/baselines.json`, and the gate were not tuned.
Additive observational stamp: `DraftPick.acquiredByClockTrade?` is
written in `tryCpuClockTrade` after `executeTrade` and never read by
`cpuPick` / valuation. Harness: `v2/scout-audit.ts` arms `control` and
`fo` (not registered).

**Question.** Auto-pick for the user club ran ~+2 true points per
slot above CPU neighbours in every scouting-audit arm — including
`control`, where the user drafts through the CPU's own `cpuPick`.
That is not scouting (user share q = 1.000). Two candidates, one
number each:

| candidate | if this is the cause |
|---|---|
| (a) the user's FO dials | `fo` user slot value collapses toward 0 |
| (b) winner's curse on CPU clock move-ups | clock-acquired slot value vs original-owner neighbourhood is negative |

**Verdict (cloud VM, 3 seasons × 2 seeds — directional, not lock-grade).**

- The +2 **replicates** on `control`: **+1.61** (seed 12345, n=20) and
  **+2.35** (seed 1, n=27). q = 1.000 both times.
- **(a) is not "the user has DEFAULT / a neutral FO".** Generate
  already assigns a random archetype. These two controls were Cap
  Hawk (bpa 0.70) and Secondary First (bpa 0.55).
- **(a) FO dials can still move the number.** Re-rolling to a
  need-heavy desk (bpa ≈ 0.21–0.23) took user slot value to **−0.02**
  and **+0.05**. Both `fo` draws landed on low-`bpaBias` archetypes;
  that is one child-stream accident, not a panel. Studio should plot
  `plus2.userVsCpu` against `userFrontOffice.after.bpaBias`.
- **(b) is not the +2.** Clock vs original **sign-flips**: **−0.39**
  (seed 12345) and **+1.04** (seed 1), n=72 each. Seed 1 move-ups are
  *better* than original-owner neighbours and the user is still +2.35.
  A −0.4 neighbourhood drag cannot produce +1.6 anyway.

Studio 14-season / 3-seed panel is the lock-grade read. Do not tune.

## 2. Candidate (a) — the FO profile

`cpuBoardValue` reads `frontOffice(state, teamId)` for `risk` and
`bpaBias`. The 2026-09-14 write-up called the user's FO "neutral".
**That is a slight misread of generate.** `createNewGame` already
runs `assignFrontOffices` across all 32 clubs, user included.
`frontOffice()` for the user is a shuffled+jittered archetype, not
`DEFAULT_FRONT_OFFICE` (Balanced, risk 0.50, bpaBias 0.55).

What *is* systematically even is **staff**: `refreshCpuStaff` skips
the user, so scouting share stays q = 1.000. The audit already
measured that and ruled scouting out.

The `fo` arm therefore does the experiment as specified: after
`newGame`, replace the user's FO with `makeFrontOffice` from a
random `ARCHETYPES` draw, on a child stream keyed `(seed, "plus2-fo")`
so the FO draw itself does not move the parent RNG. Staff stays
even. Same housekeeping as `control`. The first `asCpu` FA pass
then reads the new FO and the leagues diverge — `fo` is not a
matched-pair draft on the same stream. If the +2 vanishes, the
cause was this user's FO dials (or the particular generate draw).
If it persists on both `control` and `fo`, FO is not the cause —
control was already a random FO.

The JSON emits `userFrontOffice.before` / `.after` and
`scoutQuality` so a reader can see the draw.

## 3. Candidate (b) — clock-trade winner's curse

`tryCpuClockTrade` is the only CPU→CPU on-the-clock path. The buyer
is the club whose private board has a tier break; the user is never
a buyer (`seen` includes `userTeamId`). If that optimistic read is
wrong more often than not, move-up picks are worse than the slot,
the CPU neighbourhood mean drops, and the user's original-owner
picks look +2 against it.

**Tag.** After a successful `executeTrade` + `syncPicksToOwners`,
the on-clock `DraftPick` is stamped `acquiredByClockTrade: true`.
Optional; older saves load. Not written by pre-draft trades,
`acceptClockOffer`, or `acceptMoveUp`. Not read by any decision.

**Groups**, snapshotted after `runFullDraft` / `userDraft` (draft
is still live; `enrol` runs after rollover would null it):

| group | definition |
|---|---|
| `clock` | `acquiredByClockTrade` |
| `original` | `teamId === originalTeamId` and not clock |
| `other` | offseason / draft-day trade, not clock |

**Number.** `plus2.clockVsOriginal` = slot value of clock CPU picks
against the original-owner CPU neighbourhood (±8, min 5 peers).
Negative ⇒ move-ups pay the winner's curse. `otherVsOriginal` is
reported so pre-draft trades do not hide in the clock cell.

Slot value is draft-time. It does not need the four-year mature
cutoff. A 3-season run still emits it.

## 4. Cloud VM read (path-proof)

This box cannot run the 14-season / 3-seed panel. Path-proof:
**3 seasons**, seeds **12345** and **1**, arms `control` and `fo`.
Outcome labels are empty (mature cutoff is `season − 5`); the
numbers are draft-time slot value on every drafted class.
`scoutQuality` = **1.000** on every run. Clock trades hit
`CLOCK_TRADES_MAX` (**24**) every draft; almost all sit in R1–2
(66–69 of 72).

| arm | seed | user FO | risk | bpa | user n | user vs CPU | clock n | clock vs original |
|---|---:|---|---:|---:|---:|---:|---:|---:|
| `control` | 12345 | The Cap Hawk | 0.46 | 0.70 | 20 | **+1.61** | 72 | **−0.39** |
| `fo` | 12345 | Old-School Ground Game | 0.29 | 0.23 | 17 | **−0.02** | 72 | −2.54 † |
| `control` | 1 | The Secondary First | 0.41 | 0.55 | 27 | **+2.35** | 72 | **+1.04** |
| `fo` | 1 | The All-In Operator | 0.78 | 0.21 | 26 | **+0.05** | 72 | +1.71 † |

† `fo` clock cells are a diverged league (user FO changes `asCpu` FA
before the first draft, so the parent stream moves). Do not pool
them with `control` for candidate (b). The (b) numbers are the two
`control` clock cells.

**On (a).** The 2026-09-14 "neutral profile" is not what generate
does. Both control FOs are shuffled archetypes, both still +2. The
`fo` arm did not test "random vs default" — it tested "this
generate draw vs a second draw". Both second draws were need
drafters (bpa 0.21–0.23) and both ate the +2. That is compatible
with `bpaBias` (a high-BPA user beats a mixed-CPU neighbourhood; a
need drafter does not) and also compatible with 3-season noise.
It is **not** a closed verdict. Studio: three `fo` seeds, and the
bpaBias scatter.

**On (b).** Winner's curse is not a stable sign on 3-season
control. Seed 1's move-ups run **+1.04** and the user is still
**+2.35**. If clock picks were pulling the CPU mean down, a
positive clock cell would shrink the user number, not enlarge it.
(b) is not the +2. The clock market may still be mispriced; that
is a different question, and this short panel cannot sign it.

  is on the live `DraftPick`; `d.clockTrades` is the count.
- Snapshot origins in the draft phase, before `enterCampAfterDraft`
  / rollover. `enrol` runs after the offseason loop; `state.draft`
  is null by then.

  `tryCpuClockTrade`) before the draft-phase `runFullDraft`. The
  stamp is inside `tryCpuClockTrade`, so both halves are tagged.

  original-owner CPU picks only — including other clock picks in
  the neighbourhood would shrink a real curse.
