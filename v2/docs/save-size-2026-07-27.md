# Save size — the P4 fix

The audit's P4 said the save grows about 1 MB a season and is ~20 MB by season 20, with
current-season box scores a flat ~10.5 MB on top. `drift.ts` carried it as a known-failing
`P1` guard. This is what it actually was and what was done about it.

## Where the bytes were

`scripts/savesize.ts` (new, `npm run savesize`) plays N seasons and sizes every field of
`GameState` at each rollover. Seed 12345, 20 seasons, before any of this:

| | season 1 | season 20 | per season |
|---|---|---|---|
| total | 14.41 MB | 34.48 MB | +1.06 MB |
| players | 2.28 | 20.13 | +0.94 |
| &nbsp;&nbsp;of which retired | 0.00 | 13.71 | +0.72 |
| &nbsp;&nbsp;of which `player.stats` | 0.83 | 16.09 | +0.80 |
| games (box scores) | 12.01 | 11.85 | flat |
| log | 0.03 | 2.35 | +0.12 |
| history + records + teams + picks | 0.09 | 0.13 | ~0 |

Two separate problems, and the audit had conflated them:

- **A large constant.** Box scores are current-season only, so they don't grow — but they
  are 12 MB, which is 83% of a brand-new franchise's save. A first-season player pays the
  entire cost on day one.
- **A slope.** 76% of the growth is `player.stats`, and 68% of it is stat lines belonging
  to players who have retired. Not the log, which is only 12%.

## Why not prune

The obvious move is to delete old stat lines, and it is wrong. The record book derives
season, career and franchise marks from the players' own lines at display time — that is
deliberate, and it's the reason those lists can never drift away from what happened. Only
single-**game** records are snapshotted into `state.records`, precisely because box scores
don't survive the year. Pruning stat lines would quietly rewrite the record book.

So the constraint is: keep every stat line forever, and make them cheap.

## What was done

### 1. Sparse stat rows on disk — `lib/store/codec.ts`

A stat row has ~50 numeric fields and nearly all of them are zero. Measured over 20
seasons, **the mean box-score row had 6.3 non-zero fields out of 52**: a left guard's row
is 52 keys to say he played 63 snaps, and a defensive tackle's season line carries every
passing, receiving, kicking, punting and return field at 0.

`encodeSave` drops every zero-valued number and every `false` from `SeasonStatLine`,
`PlayerGameStat` and `TeamGameStats` on the way to IndexedDB; `decodeSave` rebuilds the
full row on load. Both are wired into `saveGame` / `loadGame` / `exportSave` / `importSave`,
so nothing above `lib/store/save.ts` ever holds an encoded save.

It is lossless and self-describing — a surviving key carries its own name, so this is not a
positional format that a reordered interface could silently corrupt, and adding a field to
`SeasonStatLine` needs no change to the codec. The default for a missing key is 0, and the
key lists now live in exactly one place: the three blank constructors in
`lib/core/season/stats.ts`, which `sim/game.ts` and the codec both use. `null` is not zero
and is written out explicitly, which is what keeps a free agent's `teamId: null` distinct
from team 0's.

A tuple encoding was measured too (3.24 MB vs 3.33 MB for the same stat lines). Not worth
it: it buys 3% and costs a versioned wire format that a field reorder would corrupt.

### 2. Log trimming — `lib/core/housekeeping.ts`

The log reached 22,817 entries, and the only thing that reads it is a 40-line news feed on
the home and league pages. `trimLog`, called from `finalizeOffseason`, keeps the current
season and the two behind it in full, keeps `milestone` entries forever (titles, records,
retirements — the franchise's actual story, a few dozen a year), and drops the rest, with a
4,000-entry ceiling as a backstop. 22,817 entries → ~4,340, and 2.35 MB → 0.41 MB.

Retired players were left alone. After the codec their stat lines are 2.33 MB at season 20,
and that data is load-bearing for the record book.

## Result

| | before | after |
|---|---|---|
| new franchise, peak in-season | 14.4 MB | **3.9 MB** |
| season 20, in-season | 34.5 MB | **10.1 MB** |
| season 20, post-rollover | 19.8 MB | **8.1 MB** |
| growth per season | +1.06 MB | **+0.33 MB** |

`drift.ts`'s save-growth guard is now **live** rather than `P1`, and a second guard was
added next to it — a franchise abandoned because the browser refuses to store it is a lost
save, so the ceiling is worth asserting in its own right and not just as a consequence of
the slope.

The guard also now measures the **encoded** save rather than the in-memory object, because
the number that matters to a player's browser quota is the one that hits disk.

## Harness

- `npm run codec` — `scripts/codeccheck.ts`. Plays real seasons, then asserts
  `decode(encode(state))` is deep-equal to `state` key for key **including key order**,
  that `encodeSave` doesn't mutate the live state (the store keeps playing on the same
  object after a save; a mutating codec would corrupt a franchise one autosave at a time),
  and that a pre-codec dense save decodes to itself so no existing franchise breaks on load.
- `npm run savesize` — the composition table above, for the next time this question comes up.

## One trap worth recording

Trimming the log broke `drift.ts`'s trade guard, which counted trades as a **delta on a
running total** of `Trade:` entries. Once the log stops accumulating, that counter is no
longer monotonic and the delta collapses to zero — the guard reported "0.0 trades per
season" while trades were happening normally. It now counts entries stamped with the season
directly, which is also more correct: a league-year's trades are the in-season ones plus the
offseason that follows, and both carry that season on the entry.

Any harness that measures activity by diffing a cumulative log is making the same
assumption. There are no others today.
